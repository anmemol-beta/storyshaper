# StoryShaper 응답 속도 최적화 조사 — 2026-10-30

> 상태: 조사·선택안. 실행 경로 변경이나 실제 모델 비교 시험의 완료를 뜻하지 않는다. 공식 웹 자료 확인일은 2026-10-30 KST이며, 계정별 접근권한·요금·크레딧은 조회하지 않았다. 아래 외부 조사에는 유료 모델 호출, 모델 설치·다운로드, 서버 배포를 수행하지 않았다.

> 후속 기록: 사용자 요청으로 선택적 독립 검토·문맥 공유·구조화 출력과 이미지 저추론을 구현했다. 현재 동작과 검증은 [시험 가이드](story-agent.md#선택적-독립-검토와-속도-최적화--2026-10-30)를 따른다. 아래 내용은 조사 시점의 코드·측정 상태이며, 이후 반영된 검토 `low`의 실측도 해당 가이드에서 구분해 관리한다.

## 결론과 권장 순서

**1회 모델 호출로 해석·다음 대사·질문을 만드는 것은 가능하다. 현재도 해석과 작문은 합쳐져 있으므로, 남은 변화는 독립 검토를 같은 생성에 흡수하거나 다른 검증 수단으로 바꾸는 것이다.** 자연스러운 문장이 반드시 나빠지는 것은 아니지만, 스스로 한 번에 확인하는 방식이 별도 검토와 같은 품질을 보장하지는 않는다. 현재 승인된 낯선 재료 수용·별도 물성 검토를 유지하면서 모든 답을 무조건 1회로 처리한다는 세 조건은 검증 없이 동시에 충족한다고 주장할 수 없다.

현시점의 최선은 **현재 Spark 1.3에서 추론 예산과 호출 경계를 먼저 비교하고, 일반 경로 1회·추가 의미 검토가 필요한 경로 2회를 후보로 두는 것**이다. 엄격한 1회 상한도 별도 후보로 비교하되, 로컬 검증 실패 때는 준비된 안전한 내용과 즉시 터치 보기로 끝내며 추가 모델 재시도로 시간을 늘리지 않는다. 이때 새 재료 수용률이 떨어지면 기존 기능과 동등한 개선으로 인정하지 않는다.

| 우선순위 | 비교할 변경 | 기대 효과와 판단 기준 |
| --- | --- | --- |
| 1 | 기본 2회 경로의 실제 시간·품질 기록 → 독립 검토의 `default / low / minimal` 비교 | 기존 구조를 보존하면서 큰 추론 비용을 먼저 줄일 후보. 현재 검토는 기본 추론이다. 낯선 재료와 안전성 평가가 필요하다 |
| 2 | 1회 해석·작문 + 서버 검증, 필요한 경우만 별도 검토하는 경로와 엄격한 1회 경로 비교 | 순차 검토 시간을 없앨 여지가 가장 크다. 검토 생략에 따른 의미 오류·과정 생략·재료 치환을 따로 평가한다 |
| 3 | 고정 사건 설명·질문은 안정된 문구를 재사용하고, 아이 답에 대한 짧은 반응만 동적으로 생성 | 프롬프트 분기 중복, 새 대사 출력, 부모 음성 캐시 누락을 함께 줄일 후보. 개인화·자연스러움이 나빠지지 않는지 확인한다 |
| 4 | Spark 음성 직접 입력 1회와 realtime 전사 + Spark 1회를 비교 | 호출 횟수보다 **아이가 말을 끝낸 뒤 실제 다음 대사를 듣기까지**가 판단 기준이다 |
| 5 | 위 구성과 동일 문답·추론 강도로 파트너 Spark Open 비교, 필요할 때 충분한 RAM/전용 GPU의 Glimmer 비교 | 공급자 변경만으로 빠르다고 단정하지 않는다. 현재 18GB Mac의 Glimmer 실행은 우선 후보에서 제외한다 |
| 공통 | 검증된 그림·음성의 사전 생성·캐시와 승인 후 독립 미디어 작업의 병렬 실행 | 새 그림·낭독이 남은 병목이면 텍스트 호출만 줄여서는 전체 기다림이 충분히 줄지 않는다 |

이는 구현 승인이나 모델 선택 확정이 아니다. 이번 요청은 로드맵 단계 1~2와 §13의 턴 지연 단축을 위한 조사이며, 실행 코드는 변경하지 않았다.

## 현재 코드에서 확인한 실제 경로

확인 대상은 `aa29820` 위의 **미커밋 변경을 포함한 작업 트리**다. 같은 작업 공간에서 음성·UI 수정이 진행 중이므로 오래된 문서의 통합 상태보다 아래 실제 코드를 우선했다.

- [엔진](../../story_agent/engine.py)의 기본 `pipeline`은 `two_call`이다. 정상 자유 입력은 `interpret_compose` → 서버 해석·초안 검사 → `review` → 상태 확정 순서다. `legacy_three_call`은 명시적으로 고를 때만 사용한다. 거절·오류 경로의 호출 수는 달라질 수 있다.
- [제공자](../../story_agent/provider.py)는 `muse-spark-1.3`과 Responses API를 사용한다. 합친 첫 호출에는 `reasoning.effort: low`, 검토에는 추론 강도를 지정하지 않는다. 상한은 추론을 포함한 8,192 토큰, 요청별 제한 30초다. 현재 코드는 스트리밍·JSON Schema 강제·명시적인 지속 연결 풀을 사용하지 않는다. 캐시 토큰은 측정하지만 캐시 적중을 보장하지 않는다.
- [서버](../../story_agent/server.py) 기준 텍스트 답은 이미 브라우저에서 `/api/answer` **한 번**으로 제출한다. 이 요청 안에서 제공자 모델을 두 번 호출한다. 바깥 HTTP 요청을 하나로 감싸는 것과 실제 추론 호출을 줄이는 것은 다르다.
- 준비된 `choiceId` 선택은 서버가 검증하고 작성된 대사로 진행하므로 **모델 0회**다. 빈 답·일부 로컬 차단도 0회다. 단순 자유 발화가 등록 재료와 일치한다는 이유만으로 모두 0회 처리되는 것은 아니다.
- [음성 입력](../../speech/transcribe.py)은 녹음 변환 후 Muse Voice에 별도 전사를 요청한다. [에이전트 화면](../../prototype/agent.js)은 전사 내용을 채운 뒤 사용자 확인·제출을 받는다. 고정 그림책의 [2.5초 확인 창](../../prototype/app.js)을 이 화면의 모델 지연으로 합산하면 안 된다.
- [부모 음성 코드](../../narration/server.py)는 Chatterbox를 한 번 로드해 유지하고, 대사별 캐시와 한 생성 작업자를 사용한다. [화면 모듈](../../prototype/narration.js)은 실제 응답 뒤 대사를 큐에 넣고, 이미 만든 짧은 맞장구를 먼저 재생할 수 있다. 영어 부모 음성·한국어 브라우저 음성 경로를 구분해야 한다. [낭독 기록](../../narration/README.md)의 새 줄 3~6초는 기존 검증 기록이며 이번 재측정 결과가 아니다. 맞장구가 곧바로 들려도 다음 이야기의 준비 시간이 줄었다는 증거는 아니다.
- 로컬 미디어는 현재 등록 자산과 전달 계약이 중심이다. Muse Image 12~20초는 [별도 API 실험](api-test.md)의 과거 단회 수치이며 현재 통합 화면 전체의 측정치가 아니다.

### 통합 호출의 문맥 크기 확인

오프라인 기록용 제공자로 한국어 첫 질문에 `아이스크림`을 답하고, 현재 `two_call`과 현재 코드의 `legacy_three_call`을 비교했다. 전송 본문은 실제 어댑터와 같은 직렬화 규격으로 계산했다. 검토 대상은 모형 제공자의 준비된 초안이므로 실제 생성 결과의 요청 크기는 달라진다.

| 경로 | 호출별 요청 본문 바이트 | 합계 |
| --- | --- | ---: |
| 현재 2회 | 해석·작문 13,646 + 검토 3,926 | 17,572 |
| 현재 코드의 비교용 3회 | 해석 2,775 + 작문 3,697 + 검토 3,926 | 10,398 |

첫 합친 요청에는 등록 재료 5개와 새 재료 물성 4개의 **총 9개 전이 초안**이 들어간다. 이 사례에서는 호출이 줄어도 전송 본문은 약 69% 커졌다. 이는 입력 토큰이나 지연이 69% 늘었다는 뜻이 아니다. 다만 ‘3회→1회이므로 무조건 3배’라는 계산을 뒷받침하지 않는다. 다음 장면 선택은 서버가 유지하고, 모델에는 여러 분기의 완성 대사를 중복 전송하기보다 공통 구조·물성별 차이를 간결하게 제공할 여지가 있다. 부정·복합 재료를 단순 문자열 매칭으로 먼저 확정해 프롬프트를 줄여서는 안 된다.

## 실제 측정에서 확인한 병목과 예상 범위

원자료는 [10/29 최종 비교 JSON](benchmarks/2026-10-29-latency/optimized-final.json)이다. **과거 3회 호출·각 문답 1회**의 기록이며, 현재 2회나 제안한 1회의 결과가 아니다.

| 문답 | 당시 전체 | 그중 별도 검토 | 전체에서 검토 비중 | 검토 시간만 뺀 단순 산술값 |
| --- | ---: | ---: | ---: | ---: |
| 비닐 선택 | 31.17초 | 13.49초 | 43.3% | 17.68초 |
| 아이스크림 선택 | 25.70초 | 7.81초 | 30.4% | 17.88초 |
| 더 커질 것이라는 예상 | 15.96초 | 8.60초 | 53.9% | 7.36초 |

세 턴에서 `outputTokens` 중 추론 토큰은 각각 **96.7%, 96.5%, 92.3%**였다. 검토 응답 자체는 19토큰이지만 추론에 2,095~3,365토큰을 사용했다. 따라서 이번 자료가 가장 강하게 가리키는 병목은 내부 추론량이다. 입력 문장이나 반환 JSON을 몇 글자 더 줄이는 것만으로 해결되기 어렵다는 판단의 근거다. 토큰 생성 속도·대기열·네트워크가 분리 계측된 것은 아니므로 지연 전부를 추론 계산 시간으로 확정하지는 않는다.

현재 2회의 첫 생성을 `G`, 검토를 `V`, 1회 통합 뒤 생성을 `G'`라 하면:

`T₂ ≈ G + V + 로컬 검사`, `T₁ ≈ G' + 로컬 검사`

**검토를 없앤 만큼 줄어드는 시간과, 더 복잡해진 한 호출이 늘리는 시간을 함께 계산해야 한다.** 과거 기록상 검토를 없앨 때 수초~10초 이상 줄일 여지는 있지만, 현재 경로의 정확한 개선률은 아직 모른다. 예를 들어 새 기준선이 생성 6초+검토 9초=15초이고 1회 생성이 6~8초라면, 6~8초 응답은 약 47~60% 단축이다. 이는 조건부 계산 예시이며 현재 앱의 측정값이나 보장치가 아니다. 기존 API 실험의 `low` 3.1초도 단순 과제이므로 전체 동화 응답의 예상값으로 그대로 쓰지 않는다.

전체 기다림에는 ASR·전사 확인·TTS·그림이 더해진다. 예를 들어 텍스트 20초를 5초로 줄여도 ASR 3초+그림 15초가 직렬이면 전체는 38초→23초다. 이 숫자도 구조를 설명하는 가정이며 통합 실측이 아니다. 승인된 상태가 준비된 뒤 그림과 낭독을 독립 실행할 수 있으면 두 작업의 합 대신 더 긴 작업이 병목이 된다. 아직 검증되지 않은 아이 답을 그대로 이미지 생성에 넘기는 방식은 현재 요구사항을 충족하지 않는다. 미리 생성하는 후보 그림은 서버가 승인한 예상 분기에서 만들어 두고, 실제 승인된 선택과 일치할 때만 사용해야 한다.

## 1회 통합에서 생길 수 있는 품질 변화

좋아질 가능성도 있다. 해석과 문장을 같은 문맥에서 만들면 단계 사이의 불일치와 네트워크·서비스 오류 지점이 줄 수 있다. 이미 개선된 자연스러움을 유지할 가능성은 있다. 다만 다음 손실은 별도로 확인해야 한다.

| 위험 | 현재 별도 검토가 확인하는 예 | 1회 경로에서 필요한 대응과 남는 한계 |
| --- | --- | --- |
| 해석 오류가 그대로 문장에 반영 | `종이컵`을 종이로, `종이 말고 나무`를 종이로 치환 | 원문 보존·부정·복합 명칭 회귀 사례. 스키마 검사만으로 의미 동일성을 증명하지 못함 |
| 새 재료 물성의 그럴듯한 오류 | 얇은 비닐과 단단한 플라스틱, 위험하거나 불가능한 재료 | 서버가 검증한 기존 사건만 사용. 미검증 재료의 안전·물성을 자유 텍스트와 enum만으로 사실로 확정하지 않음 |
| 이야기 순서·교육적 품질 손실 | 예상 전 녹은 결과를 먼저 말함, 과정 없이 결과로 점프 | 단계별 사실과 대사 범위를 서버에서 분리하고 문답 품질 평가. 기존 자동 검사도 이 오류를 놓친 실제 기록이 있음 |
| 추론 감소 또는 양자화에 따른 누락 | 아이의 틀리지만 안전한 예상을 거절, 이름·언어 혼동 | 원래 수용되던 답의 수용률과 한영 자연스러움을 속도와 함께 평가 |
| 자신이 만든 답을 자신이 승인 | 모델이 `safe:true`를 반환 | 같은 생성의 자기 판정은 별도 검토의 대체 증거가 아님. 로컬 검사와 실패 시 준비된 응답은 유지 |

1회 후보는 모델이 `interpretation + 짧은 대사 + questionText`만 반환하고, 장면·질문 ID·선택지·상태 전이·실제 물성→사건 연결은 서버가 계속 소유하도록 설계할 수 있다. 의미 검토가 필요한 새 재료를 기존처럼 폭넓게 수용하려면 당분간 그 경로의 2회 검토를 유지하는 비교안이 합리적이다. 모든 입력을 엄격히 1회로 고정하려면 같은 기준의 의미 검증 수단을 입증하거나 지원 범위를 줄이는 선택이 필요하다. 후자는 기존 요구사항의 변경이므로 ‘속도만 좋아진 동일 기능’으로 취급하지 않는다.

로컬 LLM은 API를 줄이는 대신 계산을 로컬로 옮긴다. 이번 장비는 `system_profiler`로 확인한 **Apple M3 Pro, 통합 메모리 18GB, CPU 11코어**다. 현재 Chatterbox도 MPS를 사용하므로 큰 로컬 LLM을 추가하면 메모리와 GPU를 경쟁할 수 있다. 실제 경합 측정은 하지 않았다. 별도 전용 장비·GPU를 사용할 수 있다면 판단이 달라진다.

## 다음 비교의 완료 기준 — 제안

1. **현재 2회 기준선부터 측정한다.** 기존 벤치마크는 한국어 세 문답과 최대 반복 3회에 한정돼 있다. 한영 9턴 완주, 등록·새 재료, 부정·복합 명칭, 안전한 틀린 예상, 거절·서비스 실패를 포함하는 동일 평가셋으로 넓힌다.
2. **한 번에 바꾸는 축을 제한한다.** 먼저 검토 `default/low/minimal`, 다음으로 1회·조건부 2회, 이어서 문맥 중복 축소·스키마·고정 대사 재사용을 비교한다. 첫 합친 호출의 `low/minimal`도 따로 평가한다. 같은 평가셋과 섞인 실행 순서로 시간대·부하·캐시 편향을 줄인다.
3. **빠른 오류를 빠른 성공으로 세지 않는다.** 모든 시도의 지연·오류·준비된 대체 응답 비율, 실제 수용 응답의 지연, 재료 보존·사건·과정·결말, 한영 대사 품질을 함께 기록한다. 소규모로 후보를 줄인 뒤 상위 후보에서 설정당 100턴 이상과 반복 완주를 확보해 p50/p95를 보고한다. 이 수만으로 안전성이나 통계적 확실성이 입증되는 것은 아니다.
4. **체감과 처리량을 분리한다.** 발화 종료→첫 실제 이야기 음성, 텍스트 확정, 그림 표시, 전체 미디어 준비 시각을 각각 측정한다. 맞장구 시간은 따로 기록한다. 원격 모델은 warm/cold·캐시·추론 토큰·모델 ID·리전·동시 요청 수를 같이 남기고, 로컬은 입력 처리와 batch1 생성 속도를 분리한다.
5. **마지막에 인프라를 고른다.** 현재 Spark와 파트너 Spark Open을 위 품질 기준에서 비교한다. 전용 Glimmer GPU는 cold start를 포함한 비용·p95가 실제로 유리할 때만 다음 후보로 둔다. 리전·지속 HTTP 연결 풀도 측정할 수 있지만, 이번 기록의 수천 추론 토큰보다 먼저 큰 효과를 낼 것이라고 가정하지 않는다.

이번 검증은 관련 오프라인 테스트 `tests.test_performance`, `tests.test_provider`, `tests.test_benchmark` **27개 통과**, 모형 벤치마크 **3턴·제공자 6회·전부 수용**이다. `liveLatencyEvidence:false`이며 실제 Muse의 속도·품질 검증이 아니다. 유료 API·모델 설치·런타임 기본값 변경 없이 코드 경로와 과거 수치를 확인했다.

### ‘API 한 번’에 음성까지 넣을 수 있는가

**공식 사실:** Spark의 입력은 텍스트·이미지·영상·음성·PDF, 출력은 텍스트다. [영상·오디오 이해 문서](https://dev.meta.ai/docs/video-understanding)는 Responses에 `input_audio: {data, format}`를 inline으로 넣는 예시와 MP3/WAV 지원을 제공한다. 선행 Files API 업로드 없이 inline 오디오를 넣을 수 있다. 오디오 전사 예시는 추론 예산을 포함해 최소 4,000 출력 토큰을 권장하고, 긴 오디오에서는 streaming/낮은 추론 강도를 안내한다.

**가능성에 대한 추론:** 녹음과 장면 정보를 한 번의 Spark 요청에 넣고 `transcript + interpretation + candidate`를 JSON으로 받는 방식은 문서상 기능들의 가능한 조합이다. 오디오 이해·해석·작문이 한 생성에 결합되므로 별도 Voice 전사 호출을 줄일 수 있다. 다만 **이 조합의 API 실제 동작, 아이 한국어 발화 인식, 잘못 들은 답 탐지, 저추론 품질, STT 분리 대비 속도**는 시험하지 않았다. 호출 수가 줄어도 오디오 업로드·인코딩·음성 처리 시간이 추가된다.

**범위 한계:** Muse Image의 출력은 이미지이고 Spark의 출력은 텍스트이므로, 한 번의 Spark 요청이 새 그림과 부모 음성까지 함께 만들어 주지는 않는다. Muse Voice Transcribe도 전사 전용이며 TTS나 speech-to-speech API가 아니다. 텍스트/상태 결정 **한 번**과 전체 음성·그림·낭독 파이프라인 **한 번**은 별도 목표다. [모델 입출력 표](https://dev.meta.ai/docs/models), [Voice 개요](https://dev.meta.ai/docs/overview)

별도 실험으로는 **realtime Voice 전사를 발화 도중 진행 + 발화 종료 후 Spark 한 번**도 비교할 가치가 있다. 제공자 요청은 둘이지만 전사 대부분을 아이가 말하는 동안 처리할 수 있어, 마지막 발화 이후의 체감 지연은 녹음 파일을 한 번에 Spark에 넣는 방식보다 짧을 수 있다. 이것은 지연 구조에 대한 추론이며 속도 우위의 실측 결과가 아니다. Voice의 realtime WebSocket·turn detection 제공은 [공식 Voice 설명](https://dev.meta.ai/docs/overview)에 근거한다.

### 파트너 인프라 변경

- **Baseten / Spark Open:** 공식 reasoning 문서는 항상 추론한다고 명시한다. `low/medium/high/xhigh`이고 기본 `xhigh`; `none/minimal`은 실효 `low`로 매핑된다. Meta API의 `minimal`과 동일한 동작으로 비교하면 안 된다. [Baseten Reasoning](https://docs.baseten.co/inference/model-apis/reasoning)
- **Baseten의 공개 최적화:** NVFP4, 4GPU 노드, KV cache 절감·처리량 최적화를 설명한다. 이는 아키텍처·서빙 설명이며 StoryShaper의 단일 요청이 Meta 1.3보다 빠르다는 TTFT/p95 증거는 아니다. [10/27 갱신 공식 발표](https://www.baseten.co/blog/muse-spark-open-launch/)
- **Fireworks / Spark Open:** 현행 공식 발표는 US serverless를 안내한다. 미국 리전의 총 왕복·대기 시간을 포함해 비교해야 한다. [공식 발표](https://fireworks.ai/blog/meta-muse-spark-open)
- **Fireworks / Glimmer:** 모델 카탈로그는 serverless 미지원, **2026-09-25부터 serverless 종료**, on-demand 배포는 계속이라고 적는다. ‘Glimmer를 즉시 저렴한 serverless API로 바꾸면 된다’고 가정하지 않는다. [Fireworks Glimmer 모델 페이지](https://fireworks.ai/models/fireworks/muse-glimmer-30b)
- **Modal 직접 서빙:** 모델을 계속 메모리에 올려둔 warm 실행과 scale-to-zero 이후 cold start를 나눠 측정한다. 공식 문서는 모델 초기화 등 준비가 초~분 단위가 될 수 있고, `min_containers`·`scaledown_window` 등으로 준비된 컨테이너를 유지할 수 있으나 비용이 증가한다고 설명한다. [Cold start performance](https://modal.com/docs/guide/cold-start)

따라서 ‘더 큰 GPU/가까운 리전/전용 용량’은 공급자가 허용하고 실제로 구성할 수 있는 경우에만 의미가 있다. Muse API 소비자가 Meta 내부 GPU나 배치 크기를 임의로 바꾸는 기능은 확인되지 않았다. 파트너 모델의 양자화·추론 template·모델 버전이 달라질 수도 있어 속도와 품질을 같이 측정해야 한다.

## 외부 조사로 확정하지 못한 항목

1. 모든 후보의 StoryShaper 동일 과제 p50/p95·TTFT·성공률·요금, 일시적인 제공자 혼잡의 영향.
2. 현재 계정에서 실제로 열리는 모델·파트너·리전과 크레딧 승인 상태.
3. `minimal`을 쓴 1회 통합 응답의 아동 한국어·새 재료 물성·안전성 품질.
4. Spark 음성 직접 입력+JSON 스키마 조합의 실제 실행, 녹음 파일 방식과 realtime 전사 방식의 발화 종료 후 지연 비교.
5. 대회 최신 상세 가이드·waiver·Discord 이후 공지, 외부 모델 혼합의 모든 형태와 기존 Llama 단독 사용의 적격성.
6. 충분한 RAM을 가진 별도 로컬/전용 GPU가 실제로 확보 가능한지와 운영비.

현시점 외부 근거가 뒷받침하는 순서는 **현재 Spark의 추론 예산·호출 경계·검증 범위를 먼저 비교 → 동일 평가셋으로 파트너 Spark Open 또는 충분한 메모리의 Glimmer 비교 → 음성 직접 통합과 realtime 전사의 체감 지연 비교**다. 이 순서는 제안이며 모델 변경이나 독립 검토 제거를 승인·구현한 기록이 아니다.
