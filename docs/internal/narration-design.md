# 부모 목소리 낭독: 기다림을 줄이는 생성 구조

> 2026-10-31 최신 사용자 요청: 현재 독서 화면은 본문과 질문의 **전체 음성을 준비한 뒤** 장면을 연다. 한 장면을 읽는 동안 다음 줄의 합성이나 다운로드를 기다리지 않는다. 모델을 줄마다 학습하는 것이 아니라 기존 모델로 음성을 사전 합성하는 작업이다. 아래 초기 설계와 같은 날 이전의 미준비 줄 기본 음성 정책은 이 최신 요구로 대체한다.

## 현재 장면 준비 흐름

1. 서버가 다음 이야기·질문을 확정하면 그림 준비와 `Narration.prepareScene()`을 병렬 실행한다.
2. `POST /api/voice/scene`는 화자·감정별 줄 캐시를 재사용하고 새 음성만 합성한다. 한 줄이라도 미준비이면 `status: pending`, `url: null`을 반환한다. 반복 조회가 새 합성을 만들지 않는다.
3. 모든 줄이 준비되면 24kHz 모노 PCM WAV 하나로 결합한다. 각 줄의 `lineIndex`, `speakerId`, `text`, `start`, `end`를 제공한다. 장면 길이는 최대 5분이며 긴 앞뒤 침묵만 정리하고 내부 쉼은 남긴다.
4. 클라이언트는 장면·목소리·본문·시간 구간을 확인하고 WAV 전체를 내려받아 로컬 Blob 오디오를 재생 가능한 상태로 만든다. 이때까지 이전 화면을 유지한다.
5. 그림까지 준비되면 새 그림·본문·질문을 열고 단일 오디오를 재생한다. 재생 중 줄별 HTTP 요청은 없으며 줄 강조는 파일의 시간 구간을 따른다. 이전·다시 듣기는 준비된 로컬 장면을 재사용하고 재생 위치를 유지한 일시정지를 지원한다.

처음 장면 진입과 언어·목소리 변경, 과거 장면, 수동 다음 이동에도 이 조건을 사용한다. 그림을 건너뛰어 수동 이동할 때도 낭독을 켰다면 음성 준비는 기다린다. 같은 질문의 첫 실패 터치 보기와 짧은 선택 안내는 별도 회복 경로로 바로 활성화한다.

준비 상태는 `목소리 준비 (준비 수/전체 수)`로 표시한다. 준비가 실패하거나 180초가 지나면 자동으로 부분 낭독을 시작하지 않고 다시 준비 또는 낭독 끄기를 제공한다. 다시 준비는 실패한 캐시를 복구하고 파일을 새로 다운로드한다. 구장면·구언어·구목소리의 늦은 결과는 적용하지 않는다. 목소리 삭제 시 장면 WAV와 진행 중 결합도 무효화한다.

현재 단계는 '장면 중간의 합성·다운로드 대기 제거'다. 처음 음성을 만드는 계산 시간은 장면 진입 전 준비 구간에 남고, 자연스러운 문장 쉼과 실제 기기의 오디오 재생 지연은 별도로 구분한다.

## 2026-10-31 검증

- 최초 회귀는 첫 줄 `ready`, 뒤 줄 `pending`인데 첫 MP3가 재생되어 실패했다. 수정 후 전체 준비·다운로드·재생 준비 전 재생 없음, 단일 Blob 오디오, 낭독 중 추가 HTTP 0회, 본문·질문 시간 강조를 확인했다.
- 화면은 초기 진입·이전 장면·다시 듣기·언어/목소리 변경·수동 이동·준비 실패·명시 재시도·낭독 끄기·구결과 차단·첫 실패 터치 즉시 활성화를 확인했다. 재생 오류/캐시 퇴출 자산과 잘못된 sceneKey·목소리·본문·화자·시간 구간도 차단한다.
- 서버는 손상 WAV를 명시 재시도할 때 정상 줄 캐시로 재결합하고, 손상 MP3는 해당 줄만 재합성한다. 삭제 뒤 늦은 완료가 파일을 되살리지 않으며 정상 조회가 실패를 자동 재시도하지 않는다.
- 전체 Python **334/334**, 전체 Node **171/171** 통과. `git diff --check` 통과. 실제 모델 추가 학습·유료 API 호출은 실행하지 않았다.
- 8000 앱과 소유 8100 음성 서비스를 재시작했다. 실제 캐시된 한국어 첫 장면은 본문·질문 4개 음성으로 **18.267초 / 876,884바이트** 단일 WAV가 되었고, 준비·다운로드는 해당 로컬 확인에서 약 **430ms**였다. 전체 음성이 이미 캐시된 사례이며 처음 합성 시간의 수치가 아니다. PCM 구간은 샘플 기준으로 이어진다.
- 실제 Chrome에서 기본 화면의 단일 장면 음성 재생, 일시정지·같은 위치 이어 듣기, 질문까지 끝난 뒤 완료 상태를 확인했다. 물리 iPad/Safari·새로 합성하는 모든 장면의 음질·기기별 재생 시작 시간은 이번 확인 범위 밖이다.

## 초기 설계 기록

부모가 녹음한 뒤 이야기 전체가 생성될 때까지 기다리게 하지 않는다.
**처음 몇 줄만 만들어지면 바로 읽기 시작하고, 아이가 듣는 동안 뒤 대사를 계속 만든다.**

## 숫자 (10/27, Mac M 시리즈 GPU, Chatterbox)

| 항목 | 값 |
|---|---|
| 한 줄 생성 | 약 4~6초 (평균 약 5초) |
| 한 줄 재생 | 평균 2.9초 + 줄 사이 쉼 0.45초 ≈ 3.4초 |
| 이야기 한 편 전체 대사 (모든 답 경우 포함) | 40줄 |
| 아이 한 명이 한 번 끝까지 듣는 대사 | 약 23줄 |

- **Mac에서는 생성(5초)이 재생(3.4초)보다 느리다.** 읽기만 이어지는 구간에서는 재생이 생성을 따라잡는다.
- 대신 **질문에서 아이가 생각하고 답하는 시간(5~10초)과 그림 다시 그리기(12~20초)**가 생성 시간을 벌어준다.
- 클라우드 GPU(Modal)는 아직 측정 전이다. 재생보다 빠르면 아래 구조에서 대기가 거의 없어진다.

## 구조

### 1. 시작 조건: 처음 3줄
- 녹음 직후 이야기 순서대로 생성을 시작한다.
- **처음 3줄(첫 장면 분량)이 준비되면 바로 읽기 시작한다.** Mac 기준 약 15초 대기.
- 그 15초 동안은 "목소리를 배우고 있어요" 화면에서 표지 그림을 보여준다.

### 2. 생성 순서: "곧 들을 줄"부터
생성 대기열을 **아이가 들을 순서**로 정렬한다.
1. **예상 밖 답 문장** (실시간 생성, B 방식): 생기면 무조건 맨 앞에
2. **지금 위치에서 다음에 나올 고정 대사**
3. **다음 질문의 예상 답 문장 전부** (A 방식): 질문 하나에 답 2~4개
4. 아이가 이미 답한 경로의 뒤 대사 (선택한 재료가 들어간 문장)
5. 고르지 않은 쪽 경로의 대사: 다시 읽기를 위해 마지막에, 남는 시간에

아이가 답하면 대기열을 다시 정렬한다. 고르지 않은 쪽은 뒤로 밀린다.

### 3. 재생이 생성을 따라잡았을 때
- 다음 줄 음성이 아직 없으면 **글자 하이라이트와 페이지 넘김 연출로 최대 3초 기다린다.**
- 그래도 없으면 **그 줄만 기본 목소리로 읽고** 이야기를 이어간다. 멈추지 않는 게 우선이다.

### 4. 저장
- 음성은 `(목소리 ID, 이야기 ID, 문장 해시)`로 저장한다. 문장 해시는 이미 `experiments/narration_lines.mjs`에서 쓰는 방식이다.
- **두 번째부터는 생성 없이 바로 재생된다.** 이야기 문장을 고치면 바뀐 줄만 다시 생성된다 (`generate_narration.py`가 이미 있는 파일은 건너뜀).
- 목소리 삭제 시 그 목소리 ID의 음성도 모두 지운다.
