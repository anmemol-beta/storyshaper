## 실행

Python 3.10 이상. 추가 패키지를 설치하지 않는다.

```bash
python3 -m story_agent.server
```

브라우저에서 `http://127.0.0.1:8000/prototype/agent.html`을 연다. 기존 독서 화면에는 에이전트 시험 화면 링크가 있다. 기존 클릭형 동화의 고정 대사와 분기는 별도로 유지된다.

- **Offline mock:** 규칙과 템플릿으로 동작하며 모델을 호출하지 않는다. 흐름·상태·오류 복구 시험에 사용한다. 생성 품질의 근거가 아니다.
- **Live Muse Spark:** `.env.example`을 `.env`로 복사한 뒤 `MODEL_API_KEY`를 설정하고 서버를 재시작한다. 키는 브라우저에 전달하지 않는다. 실제 모델 호출에는 계정의 사용량이 발생한다.
- 서버 포트 변경: `python3 -m story_agent.server --port 8001`.
- 검증: `python3 -m unittest discover -s tests -v`.
- 화면 실행 방식 전환 검증: `node --test tests/agent-ui.test.cjs`.
- 키 연결 후 실제 한 턴 확인: `python3 -m story_agent.smoke --language ko`. `.env`를 서버와 동일하게 읽고 키 값을 출력하지 않는다. 성공 기준은 `liveVerified: true`, `decision: accept`, `authoredFallback: false`다. `--mock`을 붙인 실행은 실제 모델 검증으로 취급하지 않는다.

초기 구현 검증은 키 없이 진행했다. 이후 2026-10-28 사용자에게 발급받은 키를 `.env`에 저장하고 실제 Muse Spark 한국어 생성·검증과 9턴 완주를 확인했다. 키는 Git에서 제외하고 파일 권한을 `0600`으로 설정했다. 키 설정 여부만으로 성공을 판단하지 않으며, 준비된 대체 대사와 실제 생성 결과를 구분한다. 전체 분기의 모델 품질·지연 평가는 별도로 필요하다.

실행 방식을 바꾸면 선택한 모델로 새 시험이 바로 시작된다. 키를 설정한 후 이전 화면이 계속 오프라인으로 표시되면 **연결 다시 확인**을 누른다. `index.html`은 고정 그림책·마이크 모의 동작을 보여주는 데모이고, 실제 자유 입력 생성은 `agent.html`에서 수행한다. 두 화면의 링크와 배너에 차이를 표시한다.

## 영어·한국어 전환

상단 **English / 한국어** 버튼으로 안내·현재 대사·질문·선택지를 바꾼다. 언어 설정은 브라우저에 저장되어 기존 그림책과 시험 화면에서 함께 사용한다. 현재 집 재료·사건·질문 단계·재시도 횟수는 유지된다. 언어 전환은 모델을 호출하지 않으며, 이미 생성된 현재 대사는 같은 장면의 검증된 번역 대사로 표시한다. 이후 새 답변은 선택한 언어로 모델에 요청한다.

이전 시험 기록과 사용자가 직접 입력한 답변은 비교·추적을 위해 당시 언어를 유지한다. 상태 검사기의 `sceneId`·`material` 같은 식별자도 언어에 관계없이 동일하다. 기존 그림책의 한국어 낭독은 브라우저 음성이며, 영어 MP3나 부모 목소리 복제를 한국어 낭독으로 표시하지 않는다.

## 질문은 어디까지 바뀌나

사람이 질문의 목적·시점·허용 답변과 사건 분기를 작성한다. 모델은 현재 상태와 확정된 분기에 맞춰 짧은 다음 내용과 질문을 작성한다. 첫 시험에서는 각 집에 재료 선택·결과 예상·이유 설명의 세 참여 지점을 둔다.

| 집의 재료 | 확정할 사건 | 그 사건을 반영하는 질문 예 |
| --- | --- | --- |
| 종이·짚 | 늑대의 바람에 흩어짐 | 바람이 불자 왜 집이 흩어졌을까? |
| 나무 | 느슨하게 쌓은 나무가 무너짐 | 나무가 무너지지 않게 하려면 무엇이 필요할까? |
| 과자 | 늑대가 과자 벽을 먹음 | 늑대가 벽을 먹자 집은 어떻게 되었니? |
| 아이스크림 | 따뜻한 햇볕에 녹음 | 무엇 때문에 집이 녹았을까? |
| 마지막 집의 벽돌·돌 | 튼튼한 집에 함께 안전하게 머묾 | 이번 집은 왜 바람에도 버틸 수 있었을까? |

표의 질문은 개념 예시다. 실제 반환 질문의 목적과 허용 답변은 메타데이터와 현재 장면을 따른다. 예상 질문에서는 아이의 다른 예측도 수용할 수 있고, 이후 실제 사건을 설명한다. 이전 사건이나 이미 정한 재료를 모델이 소급해 바꾸게 하지 않는다.

첫 두 집에서 벽돌·돌처럼 튼튼한 재료는 필수 사건과 충돌하므로 그 뜻을 인정한 뒤 다른 허용 재료를 안내한다. 마지막 집의 약한 재료도 같은 방식으로 다시 안내한다. 10/29 사용자 결정으로 낯선 재료의 해석 범위를 넓히되, 아래 검증을 거쳐 기존 사건에 연결할 수 있는 재료만 다룬다. 새 사건·배역·결말이나 전역 재료 목록을 자동으로 늘리는 기능은 아니다.

예상 답이 실제 결과와 달라도 안전하고 질문에 맞으면 아이의 생각으로 받아준다. 그 뒤 **같은 응답 안에서 관찰 가능한 과정 → 정해진 결과 → 쉬운 질문**으로 이어간다. 예를 들어 아이스크림 벽이 햇살에 말랑해지고 흘러내리는 모습을 먼저 보여준 뒤 녹은 결과를 말한다. 다시 예측하게 하는 추가 턴은 두지 않으며, 집마다 재료 선택·결과 예상·이유 설명의 세 지점과 전체 9턴 흐름을 유지한다. 준비된 대체 대사에도 같은 과정 설명을 적용한다.

## 낯선 재료의 해석과 보존 — 2026-10-29 추가 범위

다음은 사용자 승인 범위와 검증할 규격이다. 기존 별칭을 늘리는 것에 한정하지 않고 모델이 아이가 말한 재료를 해석하게 한다. 검증 가능한 모든 재료를 사전에 열거하지 않으며, 모든 낯선 답을 수용한다고 보장하지도 않는다.

해석 응답의 `material`은 기존 재료 식별자 문자열 또는 다음 모양의 제안이다. 예시의 `source`는 “비닐로 짓고 싶어!”라는 답에 실제로 나온 부분이다.

```json
{
  "source": "비닐",
  "labels": {"en": "vinyl", "ko": "비닐"},
  "behavior": "light_flexible"
}
```

서버는 제안의 필드·문자열·언어별 이름과 원문에 `source`가 포함되는지 검증한다. 현재 언어의 이름은 아이가 고른 재료명을 보존해야 하고, 번역한 이름도 같은 대상을 뜻해야 한다. 종이를 골랐는데 강철 제안으로 바꾸는 식의 치환은 허용하지 않는다. 모델이 낯선 이름이나 물성을 제시했다는 사실만으로 수용하지 않고, 기존의 별도 모델 검토 단계에서 물성·현실 가능성·아동 안전성·원문과 명칭의 동일성을 함께 확인한다.

| 제안할 물성 `behavior` | 서버가 연결할 결과 `outcome` | 장면에서 밝힐 조건 |
| --- | --- | --- |
| `light_flexible` | `blown_away` | 얇고 가벼운 재료를 느슨하게 걸친 벽이 바람에 흔들리다 풀림 |
| `loose_pieces` | `collapsed` | 서로 묶지 않은 조각이 흔들리다 빠짐 |
| `edible` | `eaten` | 늑대가 먹을 수 있는 벽을 조금씩 먹어 틈이 생김 |
| `melts` | `melted` | 따뜻한 햇살에 부드러워지고 흘러내릴 수 있는 재료의 벽이 녹음 |
| `rigid` | `stood` | 단단히 붙이고 함께 만든 튼튼한 벽이 버팀 |

서버가 위 다섯 기존 결과와 다음 상태를 결정한다. 첫 두 집에서 `rigid`, 마지막 집에서 나머지 약한 물성은 해당 집의 고정 사건과 맞지 않아 재안내한다. 같은 재료라도 시공 조건에 따라 결과가 달라질 수 있으므로 “이 재료는 항상 무너진다”는 식으로 설명하지 않는다.

검증을 통과한 새 재료는 세션의 집 상태에 `material: "custom"`, 제안 원문인 `materialSpec`, 안정적인 `materialId`로 보관하고 후속 질문·대사·`mediaPlan`에서 재사용한다. 한영 전환은 같은 원문·재료 식별자·사건을 보존하며 이름과 준비된 대사를 해당 언어로 보여준다. 다른 세션이나 전역 별칭 사전에 자동 등록하지 않는다.

`unsupported_material`은 뜻은 알지만 현재 검증 범위로 진행하기 어려운 재료, `unclear_answer`는 뜻이 모호한 답으로 구분해 안내한다. 입력 실패 횟수·3회 보기 전환 정책은 유지한다. 제안 스키마 오류·잘못된 물성·검토 실패 같은 모델 문제는 기존 서비스 오류 경로로 처리하고 아이 실패로 집계하지 않는다. 결과·미디어 계획은 검증이 끝난 뒤에만 확정한다. 이 규격의 새 테스트·실제 모델 품질 검증 결과는 확인 후 별도로 기록한다.

## 구성과 데이터 경계

- `story_agent/story.json`·`story_agent/story.ko.json`: 언어별 고정 이야기·재료·결과·질문 의도와 대체 답변.
- `story_agent/engine.py`: 답 해석, 서버가 결정하는 진행, 대사·질문 생성, 별도 모델 검토, 규칙 검증, 질문별 실패 집계와 미디어 전달 계획.
- `story_agent/materials.py`: 낯선 재료 제안의 스키마 검증과 다섯 물성에 대응하는 과정·사건·질문의 준비 문구. 실제 재료 의미·물성·아동 안전성을 확인하는 별도 검토를 대체하지 않는다.
- `story_agent/provider.py`: 공식 Meta Responses API 호출. 서버의 지시와 사용자 데이터를 분리하고 `store: false`를 사용한다. API 오류 본문·키를 화면이나 진단 로그에 출력하지 않는다.
- `story_agent/server.py`: 로컬 HTTP 서버·메모리 세션·요청 중복 방지·질문 버전 검증. 저장소 전체를 공개하는 정적 서버가 아니며 `prototype/`의 파일만 제공한다.
- `prototype/agent.*`: 텍스트 입력·대사·질문·판정·재시도·세 가지 선택지·상태 확인 화면. 사용자가 입력한 테스트 답과 기록은 로컬 저장소에 보관하지 않는다.

모델에 전체 진행을 맡기지 않는다. 첫 호출의 해석·대사 초안을 받은 뒤 서버가 해석의 허용값과 다음 사건·질문을 결정하고 초안을 검증한다. 두 번째 호출은 서버가 정한 문맥에서 대사·질문을 독립 검토한다. 오류나 검증 실패는 이야기 상태를 진행시키지 않으며, 미검증 문구를 표시하지 않는다. 모델을 사용한 검토와 규칙 검사는 콘텐츠의 절대적 안전이나 임상적 적합성을 보장하지 않는다.

## API

모든 요청은 같은 로컬 서버에서 보낸다. JSON 응답만 사용한다.

| 요청 | 입력·결과 |
| --- | --- |
| `GET /api/config` | `{liveAvailable, model}`. 키 자체는 반환하지 않는다. |
| `POST /api/sessions` | `{mode: "mock" 또는 "live", language?: "en" 또는 "ko"}` → 초기 상태 |
| `POST /api/language` | `{sessionId, version, language}` → 진행을 유지한 언어별 상태 |
| `POST /api/answer` | `{sessionId, version, questionId, requestId, answer, choiceId?}` → 처리 후 상태 |

반환 상태는 `language`, `sessionId`, `version`, `sceneId`, `question`, `lines`, `decision`, `reason`, `attempts`, `choiceMode`, `storyState`, `mediaPlan`, `diagnostics`, `providerMode`를 포함한다. 대사는 `{speakerId, text}`, 질문은 `{id, text, intent, choices}`다. 다음 질문이 없으면 `question`은 `null`이다.

- `decision`: `ready`, `accept`, `clarify`, `redirect`, `service_error`, `complete`.
- `requestId`: 같은 발화를 네트워크 재시도할 때 같은 값을 사용한다. 동일 요청은 다시 집계·생성하지 않는다. 다른 내용에는 새 ID를 사용한다.
- `version`·`questionId`: 서버의 현재 상태와 일치해야 한다. 오래된 질문에 답하면 HTTP 409와 현재 상태를 반환한다. 클라이언트가 보낸 이야기 상태는 신뢰하지 않는다.
- `choiceId`: 세 번 실패 후 표시한 현재 질문의 검증된 선택지에만 사용한다.
- 인식 실패·허용 범위 밖 답은 같은 질문에서 합산한다. 세 번째 실패 직후 `choiceMode`로 전환한다. 모델·네트워크 오류는 `attempts`에 포함하지 않는다.
- 서버는 세션별 동시 요청을 차단하고 세션당 최대 60회 시도를 허용한다. 메모리 세션은 2시간 후 만료되며 서버 재시작 시 사라진다. 이는 운영용 영속 저장·계정·가족 권한 구현이 아니다.
- 모델 장애나 출력 검증 실패에는 아이 실패 횟수를 올리지 않고 준비된 선택지 세 개를 바로 제공한다. 해당 선택지는 추가 모델 호출 없이 검증된 대사·분기로 진행한다. 화면과 `diagnostics.authoredFallback`에서 이 대체 경로를 표시하며 실제 AI 생성 성공으로 표시하지 않는다. 자유 입력으로 모델 재시도도 가능하다.

`mediaPlan`은 승인된 사건·변경값을 후속 담당자에게 넘기기 위한 데이터다. 이 구현은 실제 이미지·영상 생성이나 결과 검수를 호출하지 않는다. 화면 그림도 고정 참조 이미지이며 새로 생성된 결과로 표시하지 않는다.

## 응답 속도 계측과 비교 — 2026-10-29

이 절의 비교 결과는 기존 **3호출** 경로의 이력이다. 10/30 통합 후 기본은 2호출이며, 현재 벤치마크도 새 경로를 실행한다. 아래 9회 상한·35회 실측과 과거 JSON을 새 실행의 호출 수나 성능으로 해석하지 않는다.

사용자 요청의 1·2·3번(계측·낮은 생성 추론·단계별 프롬프트 축소)을 적용했다. 해석→서버 전이→생성→독립 검토의 세 호출과 검증 후 표시를 유지한다. 재료 선택에는 재료 목록·새 제안 규격을, 예상·이유 해석에는 현재 질문과 승인된 재료·과정을 보낸다. 생성·검토는 전체 집 이력 대신 현재 전이 사실과 초안·질문·배역·결말을 사용한다. 예측 단계에만 생각 인정→관찰 과정→결과→쉬운 질문 지시와 예시를 추가한다. 재료 선택 응답에는 미래의 관찰 과정 데이터를 보내지 않고, 집을 짓는 설정까지만 설명한 뒤 예상 질문을 하도록 생성·검토 양쪽에 명시한다.

- 생성 요청만 `reasoning: {effort: "low"}`를 사용한다. 해석·검토에는 강도를 지정하지 않는다. 공식 문서상 생략해도 모델이 자체 수준으로 추론한다. 출력 상한 8,192는 추론+최종 출력의 상한이며 유지한다. 키·제공자·타임아웃·재시도 정책은 그대로다.
- 시험 화면의 **진단 정보 보기** 안 `performance`에서 `totalMs`, `modelCalls`, `calls`를 확인한다. 호출별 `phase`, `durationMs`, `completed`, `instructionChars`, `inputChars`, `requestBytes`, `reasoningEffort`, `inputTokens`, `outputTokens`, `reasoningTokens`, `cachedInputTokens`를 제공한다. 토큰은 제공자가 보고한 수치만 사용하며 없으면 `null`이다. `outputTokens`에 `reasoningTokens`가 포함되므로 합산하지 않는다.
- `completed`는 모델 응답 파싱 완료이며, 검토 수용·최종 상태 확정은 최상위 `decision`·`diagnostics.validated`로 확인한다. 오류 시 시도한 호출까지 기록한다. 빈 입력·로컬 거절·대체 선택의 호출 수는 0이며 이전 턴의 측정을 가져오지 않는다. 이미 결말인 엔진 상태에 직접 다시 답하면 기존과 같이 동일 스냅샷을 반환한다. HTTP API는 결말 뒤 답변을 받지 않는다.
- 성능 기록에는 발화·생성 원문·키·제공자 오류 본문을 넣지 않으며, 서버 로그로 자동 출력하지 않는다. 기존 세션·중복 요청 응답에는 해당 턴의 동일 측정값을 보존한다. 언어 전환은 별도 모델 요청을 하지 않는다.
- 오프라인 모드의 호출 수는 규칙 제공자 호출 수이며 실제 원격 모델 요청이 아니다. `providerMode`·벤치마크의 `liveLatencyEvidence`와 함께 해석한다.

반복 가능한 고정 문답 벤치마크(기본값은 오프라인):

```bash

python3 -m story_agent.benchmark --live --compose-effort default --label default --output /tmp/default.json
python3 -m story_agent.benchmark --live --compose-effort low --label low --output /tmp/low.json
```

10/29 비교 당시에는 비닐 선택·아이스크림 선택·“더 커질 거 같아!” 예상의 세 턴, 최대 9회 호출이었다. 현재 기본 2호출 벤치마크는 세 턴에 최대 6회 호출한다. 선택 실패 시 그 세션의 후속 예상을 건너뛰며 자동 재시도하지 않는다. `--repeat 1..3`으로 반복 수를 명시할 수 있다. `--live`는 기존 Meta 계정 사용량이 발생한다. `--compose-effort default`는 현재 프롬프트에서 생성 추론 설정만 생략한다. **변경 전 프롬프트까지 복원하지는 않는다.** 이번 비교의 변경 전 소스는 작업 시작 시 `/tmp/storyshaper-latency-baseline/`에 별도로 보존해 사용했다.

JSON 결과에는 지연·사용량·판정·이름 보존·추가 턴 여부만 저장한다. `processBeforeResultHint`는 한정된 어휘로 순서를 찾는 보조 신호이며 표현에 따라 `null`이 될 수 있다. 모델의 독립 검토·자동 검사 통과를 실제 아동 이해도나 자연스러움의 입증으로 해석하지 않는다. 소수 순차 실행은 제공자 부하·출력·추론·캐시 차이에 영향을 받으므로 통계적인 속도 개선 보장이 아니다.

### 실제 비교 결과

`muse-spark-1.3`, 한국어, 각 설정당 세 문답을 한 번씩 순차 실행했다. 총 실제 요청은 **35회**(9+8+9+9)이며 자동 재시도는 없었다. 최종 결과는 세 턴 모두 해석·생성·독립 검토를 실제 모델로 통과했고, 준비된 대체 대사는 사용하지 않았다.

*초기 축소 설정의 아이스크림 선택은 모델 검토와 자동 검사를 통과했지만, 생성 원문을 직접 확인하니 예상 질문 전에 물방울·흘러내림을 서술했다. 그래서 단계별 과정 데이터 분리와 생성·검토 지시를 보완했다. 자동 검사 통과와 이야기 품질을 구분해야 하는 실제 사례다. 생성 low만 적용한 실패는 독립 검토를 호출하기 전 차단됐으므로 지연 개선 성공으로 집계하지 않는다. 이 단일 실패로 low가 원인이라고 단정하지 않는다.

최종 생성 대사 직접 확인: 비닐 이름과 얇게 걸친 시공 조건 보존, 아이스크림 선택 시 건축·햇살 설정까지만 표시, 예상 답변 후 “더 커질 것 같구나!”→물방울→벽이 얇아져 흐름→녹은 결과→원인 질문 순서 확인. 예측 후 버전 2·`house1_reflect`로 이동해 추가 턴이 없었다. 전체 9턴·전 분기와 실제 아동 이해도의 최종 모델 검증은 아니다.

최종 세 턴의 입력 토큰 합계는 각각 기존 대비 약 39%·38%·43% 줄었다. 생성 단계는 기존 약 9.3~11.1초에서 최종 약 4.8~5.8초였다. 비닐 선택은 여전히 해석 12.9초+검토 13.5초가 대부분을 차지한다. 최종 아이스크림 선택의 해석 요청에만 캐시 토큰 241개가 보고됐고, 그 외 비교 요청은 0이었다. 따라서 최종 차이를 오직 프롬프트·추론 설정 효과로 분리해 단정할 수 없다. 측정 표본이 작고 초기 축소 실행에는 더 느린 턴도 있었으므로 지속적인 개선 여부는 추가 측정이 필요하다.
