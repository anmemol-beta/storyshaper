# 제출 준비와 3분 데모

> 출처: [참가자 가이드 §4·§7·§8](https://cerebralvalley.ai/e/meta-ai-developer-hackathon/details#7-submission-process-15), [공식 규정](https://cerebralvalley.ai/e/meta-ai-developer-hackathon/waiver). 확인: 2026-10-26 KST.

## 제출 경로와 마감

- 공식 제출: [Cerebral Valley 프로젝트 제출](https://cerebralvalley.ai/e/meta-ai-developer-hackathon/hackathon/submit).
- 마감: **2026-11-05(목) 11:00 KST** = 11/04(수) 21:00 EST.
- 팀 내부 권장 목표: **11/04(수) 22:00 KST까지 접수 완료**. 공식 마감 13시간 전의 제안이다.
- 팀·스타트업은 대표 1명이 **프로젝트 1건**을 제출한다. 개인별 4건 제출이 아니다.
- 개발에 참여한 **4명 모두**를 제출 페이지에 명시한다.
- 마감 이후 제출은 심사하지 않는다.

**확인 한계:** 2026-10-26 확인 당시 공식 제출 링크는 메인 행사 페이지로 돌아갔다. 따라서 실제 입력 필드·파일 형식·영상 업로드 방식·제출 후 수정 가능 여부는 확인하지 못했다. 아래 필수 항목은 참가자 가이드의 명시 내용에 근거하며, 양식이 열리면 추가 요구사항을 확인해야 한다.

## 공식적으로 준비해야 하는 내용

| 항목 | 확인된 조건 |
| --- | --- |
| 프로젝트 | 주제에 부합하고 행사 중 Meta 모델을 사용해 만든 결과물 |
| 코드 저장소 | public으로 접근 가능 |
| 데모 영상 | **3분**, 행사 중 개발한 특정 기능·코드·작동 방식을 강조, 링크 접근 가능 |
| 팀 정보 | 대표 및 개발 참여자 전원 명시 |
| 신규 개발분 | 기존 작업과 구분 가능하게 제출·영상에서 명확히 설명 |
| 작동 제품 | 영상·코드와 함께 주요 심사 자료로 쓰임. 독립 URL 필드나 배포 방식은 미확인 |
| 트랙 | 한 프로젝트당 하나 |

가이드는 “three minute demo video”라고 적는다. 정확한 허용 오차·최대 파일 크기·지원 플랫폼은 명시하지 않으므로 **약 3분이라는 이유로 초과를 허용한다고 가정하지 않는다.**

## 3분 영상 구성안 — 팀용 제안

| 구간 | 내용 | 연결되는 평가 항목 |
| --- | --- | --- |
| 00:00~00:20 | 누구의 어떤 문제인지, 기존 작업의 어려움 | Impact 30% |
| 00:20~00:35 | 해결 방식과 이번 행사에서 새로 만든 범위 | 적격성·신규 기여 |
| 00:35~02:05 | 실제 입력 → Meta 모델 동작 → 결과 → 사용자의 다음 행동 시연 | Meta 활용 25%, Demo 25% |
| 02:05~02:35 | 핵심 기술·모델의 역할·검증 결과를 간결히 설명 | 기술 20%, Meta 활용 |
| 02:35~03:00 | 결과·사용 가치·신규 기능 요약과 제품 마무리 | Impact·Demo |

이는 공식 발표 템플릿이 아니다. 가이드는 신규 기능뿐 아니라 **코드와 작동 방식**도 강조하도록 요구하므로, 핵심 구현 근거가 드러나게 구성한다. 기존 제품을 쓰면 기존 부분과 해커톤 중 개발한 부분을 명확히 구분한다. 시연 결과와 수치는 실제 검증한 것만 사용한다.

## 저장소·제품 문서 구성 — 권장

README에 아래 정보를 정리하면 심사위원이 신규 기여와 실제 작동을 이해하기 쉽다. README의 이 구조 자체가 공식 필수 양식은 아니다.

1. 프로젝트명, 대상 사용자, 해결하는 문제, 선택한 문제 정의·트랙.
2. 실제 작동 화면·3분 영상·제품 접근 링크.
3. 사용한 Meta 모델·서비스·핵심 기능과 모델의 역할.
4. 입력부터 결과까지의 동작 흐름과 주요 설계 선택.
5. 실행 방법, 필요한 환경변수 이름과 값 없는 예시.
6. 행사 중 새로 개발한 기능·코드·파일·커밋과 기존 코드의 경계.
7. 검증한 시나리오·실제 결과·현재 한계.
8. 4명 팀원과 기여 내용.
9. 사용한 오픈소스·데이터·자산의 출처와 이용 조건.

공개 저장소라는 요구만으로 특정 오픈소스 라이선스를 반드시 적용해야 한다고 단정하지 않는다. 별도 사용 코드의 라이선스 준수는 필요하다.

## 제출 전 확인

### 필수 요건

- [ ] 프로젝트가 두 문제 정의 중 하나를 충족한다.
- [ ] Meta Model API 또는 Meta 오픈 가중치 모델이 실제 프로젝트에 포함된다.
- [ ] 선택한 트랙은 하나이고 참가자 전원 자격을 확인했다.
- [ ] 대표가 팀을 대신한 제출 권한을 가졌다.
- [ ] 행사 중 신규 개발분이 기능·코드·영상·설명에서 분명하다.
- [ ] 저장소는 public이다.
- [ ] 3분 영상 링크가 정상적으로 열린다.
- [ ] 팀원 4명 전원이 제출 명단에 있다.
- [ ] 법률·정책·권리 위반 및 Anti-Projects 예시를 점검했다.

### 품질·접근성 — 권장

- [ ] 로그아웃 상태 또는 시크릿 창에서 저장소·영상·제품을 열어 봤다.
- [ ] 핵심 흐름을 반복 실행했고 오류·긴 대기·비어 있는 결과를 확인했다.
- [ ] 영상·저장소·제품·제출 설명의 모델명·기능·팀 정보가 일치한다.
- [ ] 데모와 공개 파일에 API 키·비밀번호·비공개 개인정보가 없다.
- [ ] 기존·신규 개발분 증빙과 필요한 실행 자료를 보존했다.
- [ ] 실제 제출 양식의 추가 필드를 확인했다.
- [ ] 플랫폼에서 완료 화면·접수 상태를 확인하고 기록했다.
- [ ] 수정 가능 여부를 확인하고 최종 제출 내용의 사본을 보관했다.
